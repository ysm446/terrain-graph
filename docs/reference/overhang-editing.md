# オーバーハング編集のアイデア — Heightmap + Cliff Patch

作成日時: 2026-09-20 00:04
更新日時: 2026-09-20 00:04

## 位置づけ

ユーザーが提示した LLM との会話と、その実現可能性の検討を記録する。
**未実装の機能アイデアであり、採用・着手時期・優先順位は未決定。**
既存のハイトマップ中心の設計を維持し、崖・岩棚・局所的なオーバーハングだけを
別の表面表現で補う案。汎用のメッシュスカルプトを導入する決定ではない。

## 目的と表現の使い分け

ハイトマップは水平位置ごとに高さを一つだけ持つため、垂直面やえぐれ、
上下に重なる表面を直接表現できない。地形全体を Voxel 化する代わりに、
必要な場所を局所的な Cliff Patch に置き換える。

| 欲しい表現 | 候補となる方法 |
| --- | --- |
| 地層模様、細かい亀裂 | マテリアル、法線、Triplanar mapping など |
| 輪郭を変える凹凸、岩棚、浅いえぐれ | Cliff Patch |
| 独立した大きな岩塊 | 既存のモデル配置の活用 |
| 洞窟、貫通穴、複雑なアーチ | 別途メッシュや局所 SDF を検討 |

Cliff Patch の価値は、連続した崖面の地層・張り出し・割れ目・侵食方向を
ノードとパラメータで非破壊編集できることにある。

## 表面表現の案と制約

崖に沿った基準メッシュに局所座標 `(u, v)` を設け、奥行き `D(u, v)` で変形する。
平らな崖なら「側面に立てたハイトマップ」として扱える。
湾曲した崖では基準面を崖に沿わせ、向きが大きく変わる所は分割する。

ただし、奥行きマップも測定方向に対して一価である。単一の側面マップだけでは、
厳密に水平な棚の上面や、折り返して重なる面を自由に作れるわけではない。
必要に応じて棚の上面を別の面として持たせる。ユーザーが扱う一つの崖を、
内部では複数のパッチで構成する案も含める。大きな変形による自己交差も検討対象。

想定するデータは、基準メッシュ、局所座標、奥行きマップ、地形との接続境界、
材質とマスク。解像度は地形と独立に設定できる構成を候補とする。

## 対象の指定

Cliff Patch は「傾斜 N° 以上の全領域」ではなく、**ハイトマップを超える形状を
持たせたい任意の領域**とする。45° の斜面に棚を作る場合も対象になり、
70° の単純な斜面をハイトマップのまま残す場合もある。

初期案は手動指定を基本とし、マスクで範囲を限定して、崖に沿うガイド線で
向きや広がりを指定する。既存の Path / マスクと操作の考え方を合わせるが、
既存 Path のデータや評価器をそのまま使えるかは未検討。

自動検出は補助機能として後から検討する。傾斜に加え、高低差・面積・法線方向の
連続性・曲率・ユーザーマスクを使って候補を作り、選択・除外・分割・結合できる形を想定する。
細かいノイズだけで大量のパッチを作らないことが重要。

## 元の地形との接続と非破壊編集

別メッシュを重ねるだけでは、内側へ削った場所に元地形が露出する。
えぐれまで扱うには、対象部分の元地形を描画から除外し、パッチに置き換える仕組みが必要。
描画だけでなく、影・ピッキング・表面の探索でも同じ置き換えを認識する必要がある。

主な課題:

- 接続境界の穴・段差を防ぐ。解像度や将来の LOD が異なる場合も含む。
- 法線・材質・影の継ぎ目を自然につなぐ。
- 上流の地形編集に対して基準面と境界を再生成する。
- 自動検出で領域の順序が変わっても、編集設定が別の崖に移らないようにする。
- 指定した崖が消失・分裂した場合の扱いを決める。

「ハイトマップを維持できる」ことと「小規模な追加で完成する」ことは別。
試作では、対象の固定方法と境界処理を優先して確かめる。

## 積雪との組み合わせ

既存の [CompositeSnow.hlsl](../../shaders/CompositeSnow.hlsl) は、下地の高さと雪厚の和を
近傍セルと比較して流出を求める。側面マップへそのまま適用すると奥行き差を標高差として
扱ってしまうため、崖には変形後の位置・法線を参照する処理が必要。

| 段階 | 表現 | 必要な処理 |
| --- | --- | --- |
| 被覆 | 上向き面や棚を白くする | 法線、標高、降雪方向からの遮蔽 |
| 薄い積雪 | 棚の上に厚みを作る | 雪面の変形、安定性の評価 |
| 雪の移動 | 棚から下の棚・崖下へ移す | 表面間の移送、落下先の探索 |
| 雪庇・雪崩 | 大きな張り出し、崩落、空中移動 | 追加の形状表現と運動モデル |

表面位置 `P(u,v)` に雪厚 `S(u,v)` を持たせ、重力を接平面へ投影する考え方は使える。
単位法線を `N`、重力を `G` とすると、接線方向は `G - dot(G,N) * N`。
ただし、これだけでは安定性・摩擦・輸送速度は決まらず、局所座標上の移動量へ変換する際にも
実際の距離と座標の歪みを考慮する必要がある。

`max(0, dot(N, Up))` は鉛直降雪を受ける向きの目安になるが、岩棚の下へ直接雪が
積もらないようにするには遮蔽も必要。積雪の研究例として
[Fearing, Computer modelling of fallen snow](https://graphics.stanford.edu/courses/cs448-01-spring/papers/fearing.pdf)
があり、堆積・遮蔽・安定性を分けて考える参考になる。

パッチ境界で流量を交換するだけでは、棚の途中から雪が表面を離れて落ちる挙動を扱えない。
後続段階では落下先の探索を追加する。最初は鉛直下向きに落下先を探す近似も候補。
異なる解像度の間で受け渡す量は、セル面積を考慮した体積または質量とし、
雪厚をそのままコピーして雪量が増減することを避ける。

風の表面への投影も応用候補。ただし、既存の風計算がハイトマップを障害物としている場合、
崖やオーバーハングを含む流れには障害物の扱いの拡張も必要になる。

## ノード構成の候補

以下の崖関連ノード名と接続は概念案であり、既存のピン型やノード仕様ではない。

```text
地形生成 → 侵食 → 基盤地形
                   ├→ 既存 Snow → 地形出力
                   └→ Cliff Patch → 崖の凹凸 → 崖用積雪 → パッチ出力
```

初期段階は地形と崖の雪を独立した近似として評価する。
置き換え領域では元地形とその積雪を重複表示しない。地形から崖への雪量の移送は含めない。
将来、両方をまたぐ移動を扱う段階で、共通の表面集合を計算に渡す構成を検討する。

`Surface Field` として一般化する場合は、位置・法線・雪厚だけでなく、隣接関係・距離・
セル面積・境界・遮蔽の情報も必要。ノイズやマスク演算は流用候補になるが、
Snow や侵食は計算方法の変更が必要で、既存の Heightmap フィルターが自動的に対応するわけではない。
まず崖用処理を試作し、実際の共通点が分かってから抽象化を検討する。

## 最初の試作と判断基準

試作する場合の最小範囲は、**手動指定した一つの崖を置き換え、岩棚と薄い積雪を作る**こと。
全面自動検出、洞窟、地形と崖の連続した雪輸送、雪崩、全面的な Surface Field 化は含めない。

確認項目:

1. 横から見て、元のハイトマップでは出せない張り出しやえぐれを表現できる。
2. 元地形との境界に穴や不自然な段差が出ず、内側の元地形も露出しない。
3. 上流の地形編集に追従し、指定と設定が別の崖へ移らない。
4. 棚の上には雪が積もり、棚の下には直接降り積もらない。
5. パッチ解像度と変形量に対する画質・更新時間・GPU メモリを計測できる。

## 外部出力と未決事項

追加したオーバーハングは一枚のハイトマップへ損失なく戻せない。
実用化には「地形＋崖メッシュ＋マテリアル」の出力経路が必要。
元地形の除外領域も出力先で再現する必要があり、地形の穴マスクを使うか、
周囲も含めたメッシュとして渡すかは、出力先に合わせて検討する。

採用判断前に、境界の生成方法、対象の固定方法、パッチの分割、積雪厚の定義と変形方向、
保存形式、ピン型、材質座標、LOD、出力形式を具体化する。
現段階では境界処理と編集体験を小さな試作で評価する案として保留する。
